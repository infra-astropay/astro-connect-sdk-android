# Migrate from v1.0.14 to v1.0.15 — typed `AstroStyle` colors are now `@ColorInt Int?`

The color fields on the typed `AstroStyle` API changed from hex `String?` to `@ColorInt Int?` — the same color representation used across the Android platform (Compose, View XML, `ContextCompat`, etc.). This affects:

- `AstroStyle.backgroundColor`
- `AstroHeaderStyle.backgroundColor`
- `AstroHeaderStyle.borderColor`

Any code that passes a hex string to one of these fields will no longer compile. You have two options: pass a native color (recommended), or keep the hex string by moving the value into the `styleOverrides` map.

## Before

```kotlin
val style = AstroStyle(
    backgroundColor = "#FFFFFF",
    header = AstroHeaderStyle(
        backgroundColor = "#EFEFEF",
        borderColor = "#CCCCCC",
    ),
)
```

## After — option 1: pass a native color (recommended)

Each field now accepts a `@ColorInt Int`. Any of the standard Android construction forms work — a Compose `Color` converted with `.toArgb()`, an ARGB literal, or `Color.parseColor(...)`:

```kotlin
val style = AstroStyle(
    backgroundColor = Color.White.toArgb(),
    header = AstroHeaderStyle(
        backgroundColor = Color(0xFFEFEFEF).toArgb(),
        borderColor = android.graphics.Color.parseColor("#CCCCCC"),
    ),
)
```

All three accept an alpha channel — pass an 8-digit ARGB value (e.g. `Color(0x80EFEFEF).toArgb()`) for partial transparency.

## After — option 2: keep the hex string via `styleOverrides`

If you must keep colors as hex strings — for example, theme values fetched from a remote configuration service — move them into `AstroConfiguration.styleOverrides` instead of the typed `AstroStyle`. The map accepts both hex strings (6- or 8-digit `#RRGGBB` / `#RRGGBBAA`) and `androidx.compose.ui.graphics.Color` values for color leaves.

The header colors have a dedicated nested key. Move `AstroHeaderStyle(backgroundColor = "#EFEFEF", borderColor = "#CCCCCC")` into `styleOverrides["header"]["backgroundColor"]` / `["borderColor"]` — these style the native header and follow the same precedence (`styleOverrides` wins over the typed `AstroStyle.header.*`):

```kotlin
val configuration = AstroConfiguration.builder()
    .setEnvironment("sandbox")
    .setAppIssuer("your-app-issuer")
    .setClientId("your-client-id")
    .setPartnerUserId("your-partner-user-id")
    .setAccessToken("your-access-token")
    .setStyleOverrides(mapOf(
        "backgroundColor" to "#FFFFFF",
        "header" to mapOf(
            "backgroundColor" to "#EFEFEF",
            "borderColor" to "#CCCCCC",
        ),
    ))
    .build()
```

See [Free-form overrides via `styleOverrides`](../STYLE-TOKENS.md#free-form-overrides-via-styleoverrides) for the full key catalog and contract. Note that the typed `AstroStyle` and `styleOverrides` are independent: `styleOverrides` mirrors the typed key shape but is a separate free-form passthrough.

## Mapping

| Field | Before | After |
|---|---|---|
| `AstroStyle.backgroundColor` | `String?` (hex) | `@ColorInt Int?` |
| `AstroHeaderStyle.backgroundColor` | `String?` (hex) | `@ColorInt Int?` |
| `AstroHeaderStyle.borderColor` | `String?` (hex) | `@ColorInt Int?` |

## Caller-facing impact

- Any call site that passes a hex `String` to one of the three fields above will produce a compile error. Convert the value to a `@ColorInt Int`, or move it into `styleOverrides`.
- The non-color fields on `AstroStyle` and `AstroHeaderStyle` (e.g. `borderWidth`, `paddingHorizontal`, `paddingVertical`) are unchanged.
- This is the only breaking change in v1.0.15. The rest of the style-customization surface is additive.
